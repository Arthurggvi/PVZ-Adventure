# 奇境大陆｜8K 运行管线与动效接入

## 入口与坐标

- 正式地图为 `res://scenes/adventure/wonderland_map.tscn`。大陆地图入口与返回仍使用已有目录和 SceneTransition。
- 底图采用用户提供的 8192×4096、10bit BT.2020/PQ AVIF。经浮点 BT.2390 色调映射与感知色域映射生成原尺寸 sRGB 显示图，再以 8 张无损 PNG 图块绘制；内部边界各保留二十四像素采样边，覆盖最多四世界单位的水面合成位移。
- 世界范围仍为 1774×887，密度为 `8192 / 1774`。地区、枢轴、索具和 CPU 悬停 ID 图都用世界单位；显示蒙版像素大小不能直接用于查询世界坐标。
- `art_layout.json` 保持 schema 3，`terrain` 声明原生分辨率、密度、采样区及不重叠的核心区。水面覆盖按核心半开边界裁切，只在位移采样时使用留边，避免重复叠加亮纹。地标配置为 schema 2，区域效果配置为 schema 1。
- 11 个地区轮廓仅提供悬停高亮；独立节点提供名称和地区介绍。当前均为 `stage_reference=null`，用户已确认先接地图界面、暂不启用战斗入口；节点点击不进入僵尸岛关卡，也不写入通关进度。

## 导航与显示

- 固定可见世界高度 336，对应约 1551.58 个源像素。相比高度 312 的上一版，主体显示大小再缩小约 7.14%；1440p 下有足够源像素进行轻微缩小采样。窗口改变时保持构图尺度；超宽窗口优先覆盖边界。
- 项目 `canvas_items` 直接以窗口分辨率绘制；1066×600 是逻辑基准，不是低清离屏缓冲。导入保持无损、不限尺寸、不生成低清替代图；不使用锐化或最近邻放大。更高分辨率屏幕仍受当前视野内的源像素数量限制。
- 边缘热区随窗口高度取7.5%，至少28像素、至多对应轴的20%。速度随侵入深度的1.7次幂增加：1080p窗口在热区25%/50%/75%/100%深度时约为68/222/441/720屏幕像素每秒。窗口高度变化时热区与速度同比适配，对角线限制总速度。
- 左键移动至少 6 视口像素或按住 180 毫秒进入拖动；背景短按不选择地区，也不进入关卡。
- 无滚轮缩放、WASD 导航或操作指引。左上角复用僵尸岛档案头像、姓名、等级与“返回主菜单”，保留项目共享工具栏。头像和按钮上的鼠标不会触发背景手势。
- GUI、模态、切场、失焦、离窗和暂停均取消或阻断地图手势，防止拖动释放误点。

## 动效控制

- `wonderland_map.gd` 唯一推进 `elapsed_seconds`，效果总线下发时钟；高亮也用同一显示时间，0.16秒渐入渐出。
- `apply_effect_profiles` 经总线先验证整批参数，再统一提交。
- `subjects` 仅接受 `ship_seconds`、`hull_amplitude_px`、`cloth_seconds`、`cloth_amplitude_px`、`ship_phase_radians`、`cloth_phase_radians`。旧漂移、升沉、旋转及桨转角字段会明确拒绝。
- `set_motion_enabled(false)` 冻结主体、水面及新环境组件当前材质帧；恢复时扣除暂停时段以保持相位连续。区域独立开关关闭覆盖、显示静态底图，且不会被全局运动恢复意外打开。交互高亮不因动画暂停而失效。
- 布料尖端最多4世界像素，采样参数按各轴实际像素密度换算；不使用全局TIME，不新增独立动画时钟。

## 致幻洋流与河流

- `ocean`、`river` 使用同一局部线性浅水高度场：384×360 网格、每格二世界单位，含岸线零通量、变深度波速、缓流输运和开口吸收。它是简化浅水模型，不是完整流体或深水色散模拟。
- `tools/art/bake_wonderland_shallow_water.py` 将十八秒近周期状态烘焙为 64 帧图集。坡度决定法线与 Snell RGB 折射，同场落点 Jacobian 决定焦散；海洋与河流配置位移上限分别为 3.2、1.7 世界单位。
- 致幻洋流使用整水体色与反光共用的线性光合成。连续多色介质以主流横纵线性投影坐标生成，通过两个中点回溯步沿解析流线迁移，复用原十八秒双相。三个折射深度样点以 Beer–Lambert 权重混合原水与染色水；染色采用原像素乘 RGB 光谱增益的 0.82 次幂、参考水色适应，再归一回原亮度，保留水纹的通道差异。
- 同波面焦散、法线受光、Fresnel 天光和 GGX 反射在同一份线性水体颜色上合成，反射仅借用弱共享色偏，不再叠独立薄膜珠光。短波法线权重为 0.16，`GGX alpha²=0.038`，最后仅做一次软肩部与显示颜色转换。算法仍是二维原画的美术近似，不是完整三维体积光线追踪或原生 HDR 输出。
- 主菜单参数校验及显式周期入口继续复用。`dream_strength` 在海洋为 0.9、河流为 0；取 0 时回到原水面兼容路径，0～0.12 平滑交接，达到 0.12 后只执行统一光学。`spectral_strength` 为海洋 0.42、河流 0，在统一分支控制反射色偏和能量；`film_thickness_nm=520` 仅供旧薄层路径使用。`aurora_strength` 仍控制折射色散，`aurora_scale_world` 控制所选路径的介质场尺度；原画、固定缩放 336、技术流场和烘焙波面保持不变。
- `masks/water/runtime/` 中海河蒙版和流场仍为 1774×887。状态图集以同算法、同输入重烘为 `water_state_atlas.exr`，采用 RGBA half 浮点和 ZIP 无损压缩，减少八位坡度及焦散台阶被高光放大的块状痕迹。3104×2912 尺寸、每帧两像素留边、十八秒周期、通道量程和边界保持不变；无 mipmap 的理论纹理存储为 68.96 MiB，非实际显存测量。
- 本阶段遵循有界图形预览策略，不新增自动测试、性能基准或重复交互检查。历史物理场、谱域反射录像及色彩修复的检查记录不代替整水体色验收；体色版预览产物约定为 `water_dream.mp4` 和 `water_dream_240.png`，结果另行记录。模型范围、资源、参数及分版记录见 [水体说明](wonderland_water.md)。
- 海洋蒙版原路径改用 RGB：R 逐像素保留运动值，G 从既有流场完整湿域与海河份额生成体色覆盖，B 保存岸距/64。位移和表层光沿原 R 保护；体色用 B 岸距按 `1-exp(-岸距/(17+9×浓度))` 在约 22.4～26 世界单位尺度内渐入，G 只用于最后的覆盖，不在体色内部重复相乘。统一光学最后一次软肩部以 `max(0.78, base_peak)` 起算，避免无介质处压暗底图高光。`build_wonderland_water.py --refresh-color-shore` 仅更新该蒙版 G/B，不改底图、流场或物理 EXR，也不增加资源路径与加载步骤。

## 重建色彩源

原图 SHA-256 为 `4ca76eda18fbf2f703d659f3c65f0d142a6906cfa64d8a470617ce0f7789c291`，与最初整合时相同。源图没有替换。旧版 `Mobius peak=10 → RGB24` 在导入前已压缩高光、丢失宽色域表现；不能通过导入器或对旧 PNG 加亮恢复。

现在从原 AVIF 重新执行 libplacebo 浮点转换：BT.2390、同帧峰值检测（100th percentile）、perceptual 色域映射、0.3 局部对比恢复，最后量化 RGB8 时使用蓝噪声抖动。不改尺寸、不锐化、不启用 deband，保留原画细笔触。只读 1024×512 线性采样审查得到亮度峰值约 500 nit、99th percentile 约 257 nit；这些是缩小采样的统计，不作为硬编码峰值。正式转换按完整 8K 同帧统计处理。

```text
python tools/art/convert_wonderland_hdr.py --source INPUT.avif --output source_srgb.png --ffmpeg PATH/ffmpeg.exe
python tools/art/build_wonderland_hd.py --source source_srgb.png --original INPUT.avif --color-profile source_srgb.color.json --ship-backing SHIP.png --school-backing SCHOOL.png --recolor-only
```

依赖支持 Vulkan/libplacebo 的 FFmpeg、Pillow、NumPy、OpenCV；本次使用 FFmpeg 9.0.2。`source_srgb.color.json` 记录源件/显示图各自哈希与完整参数，切图前必须校验两份身份；同一记录写入 `art_layout.json.color_pipeline`。重着色同时更新地形、飞艇、两片布料，并保留现有 alpha、hover、运动安全蒙版、物理图集与动效配置。两份补底仍仅用于布幔和旗帜下方的小区域。

当前 Compatibility 渲染器输出仍是 SDR；这次修复的是 SDR 中的高光层次、色域映射和清晰度，**不是原生 HDR 显示输出**。原 AVIF 保留全部 HDR 数据。Godot 4.7 原生 HDR 输出需要 Forward+/Mobile 等支持的渲染路径；本轮没有修改全局渲染器、主菜单或启动加载流程。依据：[Godot HDR 输出](https://docs.godotengine.org/en/4.7/tutorials/rendering/hdr_output.html)、[渲染器能力表](https://docs.godotengine.org/en/4.7/tutorials/rendering/renderers.html)。
